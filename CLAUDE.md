# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

mathviz is the shared chart/control/numerics library behind [Visual Math Lab](https://github.com/apurvanakade/VisualMathLab), extracted so other sites can use it. It ships two ways from one source tree: as a **Quarto extension** (`_extensions/mathviz/`, installed with `quarto add apurvanakade/mathviz`, enabled with `filters: [mathviz]`) and as a **plain script bundle** (`dist/mathviz.js` + `dist/mathviz.css`, served from jsDelivr by tag). The README is the consumer-facing guide; this file is for working on the library itself.

## Commands

- `npm test` — `node --test` over every `src/**/*.test.js`. Tests load the real source files through `scripts/load-vm.mjs` (indirect `eval` into a stubbed `window`, in manifest order) rather than re-implementing anything. Requires `npm install` once (only `mathjs`, for the expression tests).
- `npm run build` — `scripts/build.mjs` concatenates `src/js/**` and `src/css/**` in the order `src/manifest.mjs` lists them into `dist/`, syntax-checks the JS, and copies both files into `_extensions/mathviz/dist/`. Dependency-free. **Run it before committing any change under `src/`** — `dist/` is committed and CI fails if it is stale.
- `npm run check` — test + build + `git diff --exit-code` on the built files; what CI runs.
- `quarto render example.qmd` — renders the in-repo demo page through the extension (it sits next to `_extensions/`, so no install step). The fastest way to see a change in a real page; open `example.html` and toggle the theme.
- To try the extension in another Quarto project before pushing: `quarto add /path/to/mathviz --no-prompt` from that project (a local directory is accepted; it copies `_extensions/mathviz/` in — re-run after each `npm run build`). A symlink at `_extensions/mathviz` is **not** discovered by Quarto (it checks `isDirectory()` on the raw dirent).

## Layout and the rules that hold it together

```
_extensions/mathviz/   the Quarto extension: _extension.yml, mathviz.lua, dist/ (copied by the build)
dist/                  generated bundle, committed (jsDelivr target); never hand-edit
src/manifest.mjs       THE load order, for both the build and the tests
src/js/<category>/     one VM.<category>.<fn> per file, IIFE extending window.VM; tests colocated
src/css/               tokens.css (all --vm-* defaults), then panel, chart-block, swatch, legend-controls, modebar, sliders, table
scripts/               load-vm.mjs (test loader), build.mjs
example.qmd            demo + CI smoke render
```

- **Every `src/js` file must be listed in `src/manifest.mjs`**, after anything it reads at load time; `src/manifest.test.js` enforces both the completeness and the `mustPrecede` constraints. The build inserts a `;` between JS files because each ends in `})(window)` with no semicolon, and two of those in a row parse as a call — valid syntax, so `node --check` can't catch it.
- **Version lives in three places** — `package.json`, `_extensions/mathviz/_extension.yml`, `VERSION` in `mathviz.lua` — and the build refuses to run unless they agree. The version names the `site_libs/quarto-contrib/mathviz-<version>/` folder in a consumer's output, which is what busts their cache on upgrade.
- **The Lua filter adds one html dependency per vendor `<script>` tag** (`mathviz-mathjs`, `mathviz-plotly`, and `mathviz-referrer` for the optional meta), each *before* the `mathviz` dependency that carries the bundle. Three Quarto facts force this shape, all verified against Quarto 1.7's source: (1) `quarto.doc.include_text("in-header", ...)` lands in `header-includes`, which is emitted *below* the whole dependency block, so a Plotly tag added that way loads after `mathviz.js` — and `plotly-fullscreen-button.js` patches `Plotly.newPlot` the moment it runs; (2) within one dependency `scripts` are emitted before `head`, so the tags can't share the bundle's dependency; (3) Quarto's `injectHtml` iterates a *live* `children` collection while moving nodes out of it, so a `head` string with several tags loses every second one — one tag per dependency is the workaround. `scripts`/`stylesheets` entries must be local files (Quarto copies them), hence raw `<script>` tags in `head` for the CDN URLs. A head-only dependency creates no `site_libs` folder.
- **Extension CSS loads before a project's `css:` files but after its compiled theme SCSS.** That is why every default in `src/css/tokens.css` is wrapped in `:where()` (zero specificity): a consumer's plain `:root { --vm-x: ... }` must win whatever the order. Don't unwrap them.
- **Dark mode is one selector list in two places** — `settings.darkSelector` in `src/js/plotting/chart-theme.js` and the `:where(...)` block in `src/css/tokens.css`. Change both or neither. Default: `body.quarto-dark` (Quarto's toggle), `html[data-bs-theme="dark"]`/`body[data-bs-theme="dark"]` (Bootstrap 5.3), `html.vm-dark`/`body.vm-dark` (anyone else) — root-scoped on purpose, never a bare `[data-bs-theme="dark"]`/`.vm-dark`: Quarto sets that same attribute directly on its `<nav>` to force a dark navbar independent of the page theme, and since custom properties inherit down the DOM, an unscoped match leaked the whole dark palette into the navbar on a light page (shipped in v0.1.0, fixed in v0.1.1 — see the header comments in both files for the story).
- **`src/css` targets Quarto OJS and Observable Inputs markup on purpose** — `.cell-output-display` (Quarto's per-cell output wrapper), `.quarto-layout-cell`, `form[class^="oi-"]` (Observable Inputs' generated forms). Quarto OJS is the primary host; the rules are harmless elsewhere. Observable Inputs injects its own `.oi-<hash>` rules into `<head>` at runtime, *after* any stylesheet, so a rule of ours that ties on specificity with one of those loses silently and only in the browser — out-specify it (scope under `.ojs-panel`/`.ojs-chart-controls` plus `form[class^="oi-"]`) or use `!important`, as the existing rules do.
- Prefer explicit `for`/`while` loops and `if`/`else` over `.map()/.filter()/.reduce()` chains and ternaries in `src/js` — the code is read by a Python-oriented audience. Callbacks required by an API (Plotly config values, `Plot` accessors, `addEventListener`) are fine. Stateful closures that exist for a real reason are not a style violation.
- Every new file starts with the license header for its type — see CONTRIBUTING.md.

## Releasing

Bump the three versions, `npm run build`, commit, `git tag vX.Y.Z && git push --tags`. Consumers: `quarto update apurvanakade/mathviz@vX.Y.Z`, or bump the tag in their jsDelivr URLs. Visual Math Lab pins a tag in its committed `_extensions/apurvanakade/mathviz/`; updating it there is a separate commit in that repo.

## What each function does

Every file is a small IIFE that extends `window.VM` with one function, nested under a category matching its subfolder (`VM.<category>.<fn>`) — e.g. `src/js/numerical/euler-solve.js` extends `VM.numerical` with `eulerSolve`. When adding a new category, follow the same pattern (nest under a new `VM.<category>`, matching a new `src/js/<category>/` folder) rather than adding flat top-level functions.

**`VM.expressions`**

- `src/js/expressions/make-function.js` → `VM.expressions.makeFunction(mathjs, expr)` — returns `(x) => number`, or `null` if the expression can't be parsed. Normalizes input (trim, replace `π` → `pi`), compiles via math.js, evaluates safely.
- `src/js/expressions/make-derivative.js` → `VM.expressions.makeDerivative(mathjs, expr)` — like `makeFunction` but returns the symbolic derivative.
- `src/js/expressions/make-number.js` → `VM.expressions.makeNumber(mathjs, expr)` — evaluates a constant expression (e.g. `1 + 2*3 + pi - e`) to a JS number, or `null` if it can't be parsed. Used by all numeric input fields (initial guesses, endpoints, max iterations, ...) so they accept expressions, not just literal numbers.
- `src/js/expressions/make-rational.js` → `VM.expressions.makeRational` — rational-number/fraction-reduction helper (e.g. for displaying exact Butcher tableau coefficients).
- `src/js/expressions/make-ode-function.js` → `VM.expressions.makeFunction2(mathjs, expr)` — like `makeFunction` but returns `(t, y) => number`, for ODE right-hand sides `y' = f(t, y)`.
- `src/js/expressions/make-function-of-t.js` → `VM.expressions.makeFunctionOfT(mathjs, expr)` — like `makeFunction` but binds `t` instead of `x`, for pages where the natural free variable is time (e.g. a parametric curve `x(t)`, `y(t)`) rather than a spatial coordinate.

**`VM.numerical`**

- `src/js/numerical/linear-regression.js` → `VM.numerical.linearRegression(points)` — ordinary least-squares fit of `points = [{x, y}, ...]`, returning `{slope, intercept, xlo, xhi}` or `null` if fewer than two points or a degenerate (vertical) fit. Used by every convergence-order plot.
- `src/js/numerical/l1-regression.js` → `VM.numerical.l1Regression(points, opts?)` — least-absolute-deviations line fit via iteratively reweighted least squares, seeded from `linearRegression`; same return shape.
- `src/js/numerical/polynomial-fit.js` → `VM.numerical.polynomialFit(mathjs, points, degree)` — least-squares polynomial coefficients `[c0, c1, ...]` via the normal equations (math.js does the solve).
- `src/js/numerical/euler-solve.js` → `VM.numerical.eulerSolve(f, t0, y0, tEnd, n)` — forward Euler stepper for `y' = f(t, y)`, returning the full trajectory `{ts, ys}`.
- `src/js/numerical/rk4-solve.js` → `VM.numerical.rk4Solve(f, t0, y0, tEnd, n)` — classical fourth-order Runge-Kutta stepper, returning `{ts, ys}`.
- `src/js/numerical/simpson-estimate.js` → `VM.numerical.simpsonEstimate(f, lo, hi, n)` — composite Simpson's rule quadrature (`n` must be even).
- `src/js/numerical/lagrange-quadratic.js` → `VM.numerical.lagrangeQuadratic(x0, y0, x1, y1, x2, y2, sampleCount)` — samples the quadratic interpolant through three points, returning `{xs, ys}`.

**`VM.sampling`**

- `src/js/sampling/seeded-random.js` → `VM.sampling.seededRandom(seed)` — mulberry32 PRNG factory; returns `() => number` in `[0, 1)`. Deterministic (same seed → same sequence), which is what makes a URL-shared seed reproduce the same noisy demo data.
- `src/js/sampling/gaussian-random.js` → `VM.sampling.gaussianRandom(rng)` — Box-Muller transform; takes a uniform `() => number` generator (e.g. `seededRandom`'s return value) and returns a standard-normal `() => number` generator.

**`VM.filters`**

- `src/js/filters/moving-average-filter.js` → `VM.filters.movingAverageFilter(xs, k)` — causal simple moving average over window size `k` (averages fewer than `k` samples at the start of the array, matching how the filter would run online).
- `src/js/filters/ema-filter.js` → `VM.filters.emaFilter(xs, alpha, initial?)` — exponential moving average / first-order low-pass filter, `s_i = alpha*s_{i-1} + (1-alpha)*x_i`. Without `initial`, `s_0 = x_0`; with it, `s_0` blends `initial` as the prior going into the first update (matching `kalman1DFilter`'s `x0`) — e.g. seeding from a known true starting state instead of the first noisy sample.
- `src/js/filters/kalman-1d-filter.js` → `VM.filters.kalman1DStep({xHat, P}, z, {R, Q})` — one predict+update step of the scalar Kalman filter (`R` = assumed measurement-noise variance, `Q` = assumed process-noise variance), for pages that consume measurements one at a time as they arrive; returns `{xHat, P, K}`, the new state estimate, error variance, and gain. `VM.filters.kalman1DFilter(zs, {R, Q, x0?, P0?})` — the same filter run over a precomputed array (implemented as a loop over `kalman1DStep`); returns `{xs, Ps, Ks}`, one entry per step.

**`VM.distributions`**

Closed-form densities for the standard families, plus the two helpers that turn one into something plottable. Every `*Pdf`/`*Pmf` is a pure `(x, ...params) => number` evaluated directly from the formula — no sampling, no RNG — so a chart drawn from them is exact and doesn't jitter when a slider moves.

- `src/js/distributions/log-gamma.js` → `VM.distributions.logGamma(x)` — Lanczos log-Γ, the shared building block every factorial/Beta-function normalizing constant below is computed through (in log space, so `binomialPmf(k, 500, p)` doesn't overflow on the way to a perfectly ordinary answer).
- Discrete masses: `bernoulliPmf(k, p)`, `binomialPmf(k, n, p)`, `poissonPmf(k, lambda)`, `geometricPmf(k, p)` (trials until first success), `negativeBinomialPmf(k, r, p)` (trials until the r-th success, so `r = 1` is `geometricPmf`), `hypergeometricPmf(k, N, K, n)`.
- Continuous densities: `exponentialPdf(x, rate)`, `normalPdf(x, mean, variance)` (variance, not sd), `gammaPdf(x, shape, rate)` (rate, not scale), `chiSquaredPdf(x, k)`, `betaPdf(x, a, b)`, `studentTPdf(x, k)`, `fPdf(x, d1, d2)`, `lognormalPdf(x, mean, variance)` (parameters of the underlying normal), `cauchyPdf(x, location, scale)`, `weibullPdf(x, shape, scale)` (scale, not rate).
- `src/js/distributions/sample-curve.js` → `VM.distributions.sampleCurve(fn, lo, hi, opts)` — samples `fn` across `[lo, hi]` into `{xs, ys}`. With `opts.discrete: true` it evaluates only at the integers in range instead of on a fine grid, which is what a PMF actually has support on.
- `src/js/distributions/histogram-bins.js` → `VM.distributions.histogramBins(samples, binCount, range)` — bins an array of draws, for the pages that do sample.

**`VM.plotting`**

- `src/js/plotting/padded-range.js` → `VM.plotting.paddedRange(values, opts)` — returns `{lo, hi}` with configurable padding for axis ranges.
- `src/js/plotting/chart-theme.js` → the shared chart theme, one source of truth instead of each page hardcoding its own hex literals. Every function reads the page's live `--vm-*` custom properties (declared with defaults in `src/css/tokens.css`; a site overrides them in its own stylesheet) at *call* time, not load time, so a chart built after a dark-mode toggle picks up the new theme.
  - **The `--vm-*` reading gotcha, worth knowing before touching any of this**: the light tokens are declared on `:root` but the **dark** ones under a selector that matches `<body>` (`body.quarto-dark` is what Quarto's toggle flips; the full list is `settings.darkSelector` in `chart-theme.js`, mirrored by the `:where(...)` block in `src/css/tokens.css` — keep the two identical). So anything reading them at runtime must read from **`document.body`**, not `document.documentElement` — `<html>` never matches the dark block and silently returns the *light* value in dark mode. `cssVar()` did exactly that once, which is why every chart's hover label rendered as a white box on the dark theme. Relatedly, Quarto flips the body class and swaps the stylesheet as *separate* steps, class first, so a callback that reads tokens inline on the class change still sees the outgoing theme; `onThemeChange` defers two frames for this reason. `VM.plotting.configure({darkSelector})` lets a site with its own toggle name a different selector.
  - **The chart palette lives in CSS**, as `--vm-color-<name>` tokens (`fn`, `alt`, `ok`, `muted`, `ink`, `warn`, `accent2`, `accent3`, `halo`), light on `:root` and dark under the dark selector, both in `src/css/tokens.css`. `chart-theme.js` keeps only a light-mode `FALLBACK` map for when no stylesheet is loaded (a CDN user who skipped `mathviz.css`, the Node test stub). Adding a color means adding it to `FALLBACK` *and* both CSS blocks. Chart text is set in `--vm-font-sans` (system stack by default; a site that self-hosts a font redeclares it).
  - `VM.plotting.colors()` — returns a fresh `{fn, alt, ok, muted, ink, warn, accent2, accent3, halo}` palette snapshot for whichever theme is active right now, read from the `--vm-color-*` tokens (named after what each color means on a chart — the function itself, an alternate/reference trace, a "good"/converged marker, ... — not the hex value). `halo` is the ring around a marker (white on light, the page background on dark) — use it instead of a literal `"white"`, which is a white halo on a near-black chart. Call it fresh in a page's `mainPlot`/`setup` cell rather than caching the object; see `example.qmd` (and Visual Math Lab's `apps/newton-method/index.qmd`) for the reference wiring: a `chartColors` cell feeding both `traceColors` and every `data.push(...)` color.
  - `VM.plotting.onThemeChange(cb)` — calls `cb("light"|"dark")` now and on every toggle, returning a teardown function. **This is what makes a page's trace colors follow the theme**, and every chart page needs it: the chart's chrome (background, axes, gridlines, hover label) re-themes itself via the relayout patch below, but trace colors are values the page baked into the traces it built, so they only repaint if the cell re-runs. The two-line page pattern is: `vmTheme = Generators.observe(notify => VM.plotting.onThemeChange(notify))` then `chartColors = VM.plotting.colors(vmTheme)` — `colors()` ignores the argument; it exists purely to create the reactive dependency edge. **It only fires when the theme actually changed.** `<body>`'s class list is shared — the sidebar rail writes `.vm-sidebar-open` to it whenever the sidebar opens or closes and `.vm-sidebar-pinned` on every pin — so a body-class observer that doesn't compare the theme fires on all of those too. Without that comparison this re-ran `mainPlot`, the legend and both sub-charts (i.e. rebuilt the entire chart) on each one; back when the rail also opened on hover, that meant every time the pointer touched the left edge of the screen. **Keep the guard regardless** — opening and pinning still write to `<body>`. Same guard, same reason, in `plotly-fullscreen-button.js`'s relayout observer; in both, the comparison goes *inside* the two-frame deferral, not around it.
  - `VM.plotting.colorway()` — the trace color cycle, i.e. `colors()` minus `halo` (a trace cycled onto `halo` would be drawn in the background color).
  - `VM.plotting.alpha(token, opacity)` — the same hue as a palette token (or any `#hex`/`rgb()` string) at a given opacity, for the translucent area/bar fills that pair with a solid stroke. Use it instead of an `rgba(...)` literal, which stays light-mode-colored after a toggle while its own stroke lightens, so fill and stroke drift apart.
  - `VM.plotting.subscript(n)` — `0` → `₀`, for iteration labels. Plotly trace `text` is plain text with no markup, so `x_0` renders with a literal underscore.
  - `VM.plotting.emptyState(message)` — a centered `annotations` array for when a page's `result` bailed out. Use it as `annotations: hasData ? [] : VM.plotting.emptyState("…")`, otherwise an unparseable formula draws an empty grid indistinguishable from a valid-but-empty result.
  - `VM.plotting.hoverLabel()` — the themed tooltip style. Applied per trace (not just on the layout) by the patch below, because Plotly derives a trace's hover background from *that trace's* color unless the trace sets `hoverlabel` itself, so a layout-level default never actually applies.
  - `VM.plotting.autoResize(div)` — the `ResizeObserver` every `mainPlot` needs (charts are built detached, so Plotly measures 0×0 at `newPlot` time), but one that disconnects when the div leaves the page. A bare observer outlives its div and throws `"Resize must be passed a displayed plot div element."` once a re-run replaces it.
  - `VM.plotting.layout(overrides)` — the shared Plotly layout: transparent `paper_bgcolor`/`plot_bgcolor` (so the chart shows the page's own background instead of Plotly's default `#E5ECF6` plate, and doesn't stay white-on-dark after a theme toggle), themed font/axes/gridlines/hoverlabel/`modebar`/`textfont`, `colorway`, a `transition` (zeroed under `prefers-reduced-motion`) so a step slider tweens instead of snapping, and small non-zero base margins. The transition is normally 300ms, but while `src/js/ui/slider-play.js` is running a sweep it shortens to whatever `VM.ui.playbackTweenMs` publishes — the gap between one slider value and the next — so the tween lands just before the next value arrives instead of a flat 300ms overrunning a faster gap and leaving the chart permanently mid-tween. Deep-merges a page's own `overrides` on top, so `xaxis: {title: "x", range: [...]}` extends the shared axis chrome instead of replacing it. **Don't set `margin: {l:0,r:0,t:0,b:0}` in a page's layout** — that was the old convention and it defeats `automargin`, jamming the rotated y-title and tick labels against the container edge.
  - `VM.plotting.config(overrides)` — replaces the `{responsive: true, displaylogo: false}` object every page used to copy-paste.
  - `VM.plotting.plotOptions(overrides)` — the Observable Plot equivalent of `layout()` (same font, same grid color, same palette), for the `iteratesPlot`/`convergencePlot` charts under a page's main Plotly chart.
  - `VM.plotting.themePatch()` — a **flat**, dotted-path patch (`{"xaxis.gridcolor": ..., ...}`) of just the theme-dependent style attributes, for `Plotly.relayout` specifically — `layout()`'s nested objects would replace a whole `xaxis`/`yaxis` wholesale via `relayout` and wipe out a page's own title/range. Used internally by the `plotly-fullscreen-button.js` patch below to re-theme every on-page chart the instant dark mode toggles; a page cell should not need to call this directly.
- `src/js/plotting/plotly-fullscreen-button.js` → `VM.plotting.fullscreenButton` — patches `Plotly.newPlot`/`Plotly.react` to give every chart the same modebar: a fullscreen-toggle button, no box/lasso select, and zoom in/out buttons that step by `ZOOM_STEP` (1.25× the visible span per click) instead of Plotly's own factor of 2, which overshoots when framing a curve. It also defaults `dragmode` to `"pan"` (only if a page hasn't set its own) and deep-merges `VM.plotting.layout()` underneath whatever layout the page passes, so every chart is themed with no page-level edit needed. The modebar is spelled out as an explicit `config.modeBarButtons` list — swapping the zoom buttons via `modeBarButtonsToRemove`/`ToAdd` would relocate them to the end of the bar — which is safe only because every chart on this site is 2D cartesian. On every theme flip it calls `Plotly.relayout(gd, VM.plotting.themePatch())` on every live `.js-plotly-plot`, since toggling the theme doesn't otherwise touch any OJS input and nothing else would trigger a re-render. The patching happens on load and again on `DOMContentLoaded`, is idempotent, and is a silent no-op when `Plotly` isn't on the page (`mathviz: {plotly: false}`), so no per-page wiring or explicit call is needed; a page that loads Plotly later than that calls `VM.plotting.installPlotlyPatch()`. Its theme repaint subscribes to `chart-theme.js`'s `onThemeChange` rather than owning a second body observer.
- `src/js/plotting/svg-fullscreen-button.js` → `VM.plotting.svgAspectRatio({viewBox, width, height})` / `VM.plotting.figureBounds(rects)` — the pure helpers (exported for unit tests) behind the fullscreen button on chart blocks that draw inline SVG rather than Plotly: Observable Plot output (Visual Math Lab's Sperner's Lemma apps) and hand-built `<svg>`s (Visual Math Lab's `apps/positive-predictive-value/index.qmd`). Delegated and self-installing like `src/js/ui/draggable-overlay.js`: a page opts in with `class="ojs-chart-block ojs-svg-block"` on its wrapper and **nothing else** — the module appends one persistent `<button class="vm-fullscreen-toggle">` as a direct child of the block (outside every cell's output, so a re-run that rebuilds the SVG never rebuilds the button), pins it to the top-right corner of the *figure* — the measured union of the block's figure SVGs (any `<svg>` in the block at least 64px wide, skipping the controls bar, the legend and anything inside a `button`), not the cell, since a fixed-width Plot SVG is narrower than its column (`src/css/chart-block.css` centers it there, with a selector mirroring this same figure test) and in fullscreen every figure is letterboxed into the middle — and re-measures on block/figure resize, on cell re-runs (a `MutationObserver` on the block) and on `fullscreenchange`. Clicking it fullscreens the block itself, the same element the Plotly modebar button fullscreens, so the `.ojs-chart-controls` bar comes along. Letterboxing is CSS (`.ojs-svg-block:fullscreen` in `src/css/chart-block.css`, the Plotly chain keyed on the figure): the module tags each figure SVG `vm-fs-figure` and writes its ratio as `--vm-svg-aspect` from its `viewBox` (or `width`/`height` attributes, or a measurement) — a `viewBox`'d SVG also centers its own drawing inside whatever box it gets, so a slightly-off ratio costs margin, not distortion. The chain's wrappers are flex *columns* so a `<p>` caption above a figure stays above it and the figure shrinks by the caption's height (the geometric proof's side-by-side pair — its own wrapper needs a page-local `flex-direction: row`; see that page). Same glyph as the modebar button (read from `VM.plotting.fullscreenButton.icon`), same hover-revealed pill (the hover trigger is the block, which persists across slider moves — a pill fading in from nothing on each step of a playback sweep flickers), always visible on touch. `plotly-fullscreen-button.js`'s `fullscreenchange` handler finds no `.js-plotly-plot` in such a block and skips the Plotly resize.

**`VM.ui`**

- `src/js/ui/render-table.js` → `VM.ui.renderTable({html, headers, rows})` — returns a DOM table node styled with `ojs-table` classes.
- `src/js/ui/range-progress.js` — exports nothing; keeps every range slider's `--sx` custom property equal to its value as a percentage, which `src/css/sliders.css` uses to paint the filled part of the track (Chrome has no `::-moz-range-progress`). Self-installing.
- `src/js/ui/legend-overlay.js` → `VM.ui.legendOverlay(items, {value})` — renders the floating panel of clickable swatch+label rows that toggles which traces a chart shows, in place of Plotly's own built-in legend (see the README's markup contract). `items` is `[{label, color}, ...]` in display order; `value` is the initially-checked labels, defaulting to all of them. Implements Observable Inputs' view contract (a `value` property, an `"input"` event on change), so it slots into `viewof <name> = VM.ui.legendOverlay(...)` exactly like an `Inputs.checkbox` — including `applyExampleParams`'s set-value-then-dispatch protocol.
- `src/js/ui/draggable-overlay.js` → `VM.ui.clampOverlayOffset({dx, dy, offsetLeft, offsetTop, width, height, containerWidth, containerHeight})` / `VM.ui.overlayStorageKey(pathname, role, index)` — the pure bounds arithmetic and key naming behind the drag-to-move grip on the floating chart legend (see the README's markup contract). The module is delegated and self-installing: it finds `.ojs-legend-overlay` panels itself and re-attaches to ones that appear later, so **there is no per-page wiring and nothing to call**. It deliberately does *not* touch `.ojs-chart-controls`, which sits in normal flow above the chart and has nothing to be dragged clear of. Only the two pure helpers are exported, for unit tests.
- `src/js/ui/slider-play.js` → `VM.ui.playbackDuration({min, max, step, speed})` (total sweep length in ms, `0` for a degenerate range) and `VM.ui.playbackFrame({min, max, step, elapsed, duration, mode, start})` (`{value, direction, done}` for the current point in a sweep) — the pure, rate-based arithmetic behind the play/pause button that sweeps a slider end to end. Duration scales with the slider's own stop count (`~350ms` per stop, clamped to 2–10s) rather than a page-supplied speed, which is what lets the module enhance **every** range slider inside an `.ojs-panel` or `.ojs-chart-controls` with no per-page wiring — a page opts a slider *out* instead, via `data-vm-play="off"` on the input or an ancestor. The module is delegated and self-installing like `draggable-overlay.js`, since these views are created at runtime by Observable Inputs and rebuilt whenever an upstream field changes. Each enhanced slider gets a play/pause button plus a small caret that opens a floating popover of speed presets (×¼–×4) and playback mode (Once / Loop / Bounce). **That popover is a native `[popover]`, i.e. it renders in the top layer**, and that is load-bearing rather than cosmetic: Quarto gives `.cell-output-display` — the wrapper it puts around *every* OJS cell output — `overflow: auto`, which makes it a scroll container, and a scroll container clips any descendant that escapes its box. The panel opens well above its own ~37px-tall cell, so as an ordinary absolutely-positioned child it was clipped to near-invisibility (what showed was the sliver still inside the cell's box, which reads as "cut in half"). **No z-index or stacking-order change fixes this** — only leaving the clip behind does, and the top layer is outside every ancestor's clip, so it is equally immune to the same trap arriving later via `overflow`, `transform`, `filter` or `contain` on any wrapper. **This applies to any floating UI inside any OJS cell on this site, not just this popover** — reach for `[popover]` rather than a nested absolute box. Using `popovertarget` on the caret also hands the browser toggling and light dismiss (click-outside, `Escape`, closing whichever other popover was open), all of which this module used to hand-roll. Only the position is set from script — CSS anchor positioning isn't cross-browser yet — which is also what lets it clear Quarto's fixed navbar (merely clearing the viewport's top edge is not enough; it would open *under* the navbar) and the window's right edge. Playback itself is driven by `requestAnimationFrame`, not a fixed-interval tick, so the motion is genuinely smooth rather than a stepped jump. The chosen speed/mode is a viewing preference shared across every slider on the site, stored in `localStorage["vm-playback"]` — deliberately **not** URL-synced, unlike every other input on these pages, since it is not part of the computation a shared link reproduces. While a sweep runs, the module also publishes `VM.ui.playbackTweenMs` (the gap, in ms, until the next value), which `VM.plotting.layout()` reads to size its own chart transition — see above. At most one sweep runs per page; a `once`-mode sweep stops at the maximum and the button becomes a replay glyph; playback also stops when the reader grabs the slider, when the tab is hidden, and when a cell re-run detaches the slider.
- `src/js/ui/apply-example.js` → `VM.ui.applyExampleParams(fieldSelectors, params, triggerEl)` — applies an example's params to the page's `viewof` fields by setting each view's `.value` and dispatching an `input` event, then clicks `triggerEl`'s button to run the page's normal commit flow. `fieldSelectors` is a page-local `{paramKey: cssSelector}` object of plain strings (not direct `viewof` references — see the file's comment for why: a cell that references a view whose identity is reactively recreated, e.g. a step slider capped by a "max" field, becomes reactive on it, and since this function is what changes that upstream field, a direct-reference version re-triggers itself in an endless loop). Each targetable field is tagged with a stable `data-example-field` attribute by the cell that owns it, and `applyExampleParams` looks it up fresh via `document.querySelector` at the moment it's needed. Async, with a fixed 100ms yield between fields (measured: OJS's own reactive updates settle in ~40ms, consistent with `requestAnimationFrame`-paced batching rather than same-tick propagation — a single `setTimeout(resolve, 0)` yield resolves before that finishes, silently discarding whatever the next field set once the delayed recreation lands), so a field whose bounds reactively depend on an earlier field picks up its freshly-recreated view — order params so the dependency comes first. Used by a page's "Try an example" dropdown so an example applies in place with no page reload or scroll jump. Call it from a plain DOM event listener attached once to a stable element (the `enterToPlot` pattern below), never from an OJS cell reactive on a `<select>`'s value — a native `<select>` fires both `input` and `change` per selection, so a reactive cell runs twice per selection, and the two overlapping calls race (observed corrupting a field's final value when the second pass's cascade landed after the first's).

**`VM.discreteMath`**

- `src/js/discrete-math/barycentric-triples.js` → `VM.discreteMath.barycentricTriples(N)` — every barycentric triple `[i, j, k]` (`i + j + k = N`) of a uniform order-`N` triangulation.
- `src/js/discrete-math/sub-triangles.js` → `VM.discreteMath.subTriangleTriples(N)` — enumerates the small triangles of that triangulation as triples of barycentric triples.
- `src/js/discrete-math/triangulation-edges.js` → `VM.discreteMath.triangulationEdges(N)` — every edge of that triangulation exactly once, deduped from `subTriangleTriples`.
- `src/js/discrete-math/sperner-color.js` → `VM.discreteMath.spernerColor(a, b, c)` — colors a barycentric triple per Sperner's condition (fixed vertex colors, boundary points restricted to their edge's two endpoint colors, interior points free).
- `src/js/discrete-math/random-color.js` → `VM.discreteMath.randomColor()` — uniform random red/green/blue, ignoring position; used to demonstrate violating Sperner's condition.
- `src/js/discrete-math/vertex-color.js` → `VM.discreteMath.vertexColor(name)` — the display color for a Sperner vertex color *name*: `'red'` → `colors().alt`, `'green'` → `colors().ok`, `'blue'` → `colors().fn`, read from `VM.plotting.colors()` at call time. The names themselves stay the keys every Sperner helper and page compares against (`spernerColor`, `randomColor`, `pairColor`, a page's `ColoredPoint`); only the moment of drawing goes through this, so a `Plot.dot` is `fill: d => VM.discreteMath.vertexColor(d.color)`, never `fill: "color"` (a CSS named red is not the site's red, and doesn't lighten in dark mode).
- `src/js/discrete-math/mixed-pair-color.js` → `VM.discreteMath.pairColor(colorA, colorB)` — the shared color for a two-color pair, or `null` if the colors match: red+green → `warn` (amber), green+blue → `accent3` (teal, added to the palette for exactly this), red+blue → `accent2` (purple), each via `VM.plotting.alpha` at call time.
- `src/js/discrete-math/triangle-fill-color.js` → `VM.discreteMath.triangleFillColor(colors)` — the shared fill for a rainbow (three distinct colors) triangle (translucent `accent2`, via `VM.plotting.alpha` at call time), or `'none'` otherwise.

The three color helpers read the theme when called, so a page cell that stores their output (a `mixedEdges` array, a feature's `fillColor`) must itself depend on `chartColors` — the `vmTheme`/`chartColors` pattern under `VM.plotting` above, referenced as a bare `chartColors;` line at the top of the cell where nothing else in it needs the value — or the stored colors go stale on a theme toggle. Their unit tests assert the light-theme values (the Node stub has no `<body>`, so `isDark()` is false there).
If any single `VM.<category>` grows past ~15 functions, split its doc block above further (e.g. by sub-concern) rather than letting one flat list run long — the whole point of nesting was to keep this scannable as more math functions get added.
