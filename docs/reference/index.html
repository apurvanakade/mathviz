API reference

Everything on window.VM, by category

The bundle attaches one global, VM, with a namespace per concern. Each source file adds one function (a few add two or three that belong together) and nothing here has hidden state beyond what’s noted – the theme functions read CSS at call time, the self-installing UI modules keep track of what they’ve enhanced.

Namespace What’s in it Depends on
VM.expressions typed formulas → JavaScript functions and numbers, never throwing math.js (passed in)
VM.numerical Euler and RK4 steppers, Simpson’s rule, a Lagrange parabola, L1/L2/polynomial fits – (polynomialFit takes math.js)
VM.sampling seeded uniform and Gaussian generators –
VM.filters moving average, EMA, scalar Kalman –
VM.distributions 16 closed-form PDFs/PMFs, logGamma, sampleCurve, histogramBins –
VM.plotting the theme (colors, layout, plotOptions, …), theme detection, the Plotly patch, fullscreen helpers Plotly for the patch; otherwise none
VM.ui legend overlay, results table, example presets, slider playback renderTable needs htl’s html
VM.discreteMath triangulations and Sperner colorings –

Conventions

These hold across the whole surface, so each page states only its exceptions.

Bad input gives null, not an exception. Anything that parses reader-typed text (makeFunction, makeNumber, makeRational) returns null when it can’t; a fit with too few points returns null. Branch on it and draw an emptyState.

Outside a distribution’s support you get 0. Never NaN, so a slider at an invalid parameter flattens a curve rather than breaking the chart.

math.js is passed in, not imported. VM.expressions.* and polynomialFit take the math.js instance as their first argument – the global math on a page rendered through the extension. The one exception is makeRational, which parses literals only and takes no instance.

Colors are read when you ask, not when the page loads. colors(), alpha() and the three discreteMath color helpers return whatever the active theme says right now. Call them inside the cell that builds the traces, and make that cell depend on vmTheme so it re-runs on a toggle – see onThemeChange.

Self-installing modules take no call. The Plotly patch, slider playback, the draggable legend, the SVG fullscreen button and the slider-track fill all find their markup themselves. What each looks for, and how to opt out, is in the markup contract.

What needs what

Nothing here imports anything. Where a function needs a library, it takes it as an argument or finds it on window.

Needs
VM.expressions.* (except makeRational), VM.numerical.polynomialFit a math.js instance, passed as the first argument
VM.numerical.*, VM.sampling.*, VM.filters.*, VM.distributions.*, VM.discreteMath.* nothing
VM.plotting.colors / colorway / alpha / themeName / onThemeChange / configure / subscript / paddedRange / plotOptions nothing (a document to read tokens from; sensible fallbacks without)
VM.plotting.layout / config / hoverLabel / emptyState / themePatch nothing – they build plain objects. You need Plotly to use them, of course
VM.plotting.autoResize ResizeObserver (returns null without); safe when Plotly is absent
VM.plotting.installPlotlyPatch / fullscreenButton window.Plotly
VM.plotting.svgAspectRatio / figureBounds, VM.ui.clampOverlayOffset / overlayStorageKey / playbackDuration / playbackFrame nothing – pure helpers
VM.ui.legendOverlay nothing – plain DOM. It implements Observable’s view contract; it doesn’t require Observable
VM.ui.renderTable htl’s html tag, passed in. Emits Bootstrap table classes
VM.ui.applyExampleParams views that follow Observable Inputs’ value + "input" protocol
slider playback, draggable legend, SVG fullscreen button, slider fill nothing – self-installing on the markup they look for

Where the signatures live

Every function’s JSDoc in src/js/<category>/<name>.js is the authoritative signature; these pages restate it with context and a live example. A test (src/docs-coverage.test.js) fails the build if a VM.* member exists without a heading here, or vice versa, so the two can’t drift.
